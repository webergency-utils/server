Ahead-Of-Time (AOT) Zero-Reflection Server Core

Webergency Server

Webergency Server is an industrial-grade, zero-reflection Ahead-Of-Time (AOT) compiled web server engine. It completely eliminates runtime class annotations reflection (`reflect-metadata`), dynamic parameter parsing, and runtime dependency-injection graph construction.

By offloading AST mapping and validation compilation to a pre-build compilation step, the server boasts near-instantaneous startup times, minimizes heap allocations, and executes routing and request validation with extreme microsecond-level speed.

⚡

Pure AOT Routing

Routes are mapped at build-time directly to an instructions array, removing path-regex resolution structures and string matching layers during request pipelines.

🛡️

Compiled Type Safety

Integrates with `@webergency-utils/typechecker` to extract native TypeScript interfaces and compile them directly into highly optimized JSON validators.

Core Concepts

In traditional frameworks, decorators like `@Injectable()` and `@Post()` are inspected at runtime via reflection. The server must walk class trees, parse parameter design-types, and hook up routes. This introduces boot latency and overhead.

Webergency utilizes a compiler transformer that resolves these constructs at build time:

1. TS Compilation & Transform: Compiler traverses TS files, parsing decorators and generating validator manifests.
2. AOT Manifest Emitted: Writes _metadata.webergency-server.js with routes, DI scopes, and validator functions.
3. Startup Engine Init: Core server loads the manifest. Boots instantly with no reflections.
4. Execution Pipeline: incoming requests pass directly through compiled validators, guards, and handlers.
Benefits of AOT compilation

Since validations are compiled to direct, branch-free inline JavaScript checks, the parser handles request payloads up to 10x faster than traditional library validators. In addition, memory usage is drastically reduced because no AST trees or runtime metadata caches are held in the V8 heap.

Getting Started

Install the server package along with the companion compiler plugins using `ts-patch`:

Terminal 
npm install @webergency-utils/server
npm install --save-dev @webergency-utils/typechecker ts-patch typescript
npx ts-patch install

Configure `tsconfig.json` to load the transformers in order:

tsconfig.json 
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "plugins": [
      { "transform": "@webergency-utils/typechecker/transformer" },
      { "transform": "@webergency-utils/server/transformer" }
    ],
    "experimentalDecorators": true
  }
}

Multi-Runtime Adapters

Webergency Server is engineered to be completely execution runtime-agnostic. The server detects the host runtime environment dynamically upon boot and binds standard request and upgrade pipelines onto native features:

Available Adapters

- BunAdapter: Leverages Bun's native Bun.serve() HTTP server and native Bun WebSockets for maximum throughput.
- DenoAdapter: Integrates with Deno's native Deno.serve() HTTP listener and WebSocket upgrade streams.
- NodeAdapter: Uses Node's standard http.createServer, accompanied by a custom, zero-dependency lightweight WebSocket frame parser.

Because all controllers, validations, and routes are compiled Ahead-of-Time, you can package your server application into standalone executables (e.g. bun build --compile or deno compile) with ease.

Bootstrapping the Server

To boot your application, write a bootstrapping entry point file (usually src/main.ts) that imports the compiled AOT metadata manifest and runs the Server class:

src/main.ts 
import { Server } from '@webergency-utils/server';
import { AppModule } from './modules/app.module.js';

// Instantiates the server runner
const server = new Server({
  port: 3000,
  module: AppModule,
  logs: true
});

// Starts listening and executes lifecycle initialization hooks
await server.start();

Controllers & Routing

Routing matches REST verbs mapped onto class structures annotated with `@Controller()`. Each request action points directly to a method with HTTP decorators:

src/controllers/product.controller.ts 
import { Controller, Get, Post, Put, Delete } from '@webergency-utils/server';

@Controller('/products')
export class ProductController {

  @Get('/')
  getAll() {
    return { products: [] };
  }

  @Post('/')
  create() {
    return { success: true };
  }

  @Put('/:id')
  update() {
    return { updated: true };
  }

  @Delete('/:id')
  remove() {
    return { deleted: true };
  }
}

Parameters Binding & Constraints Validation

Webergency compiler detects parameters type annotations and injects appropriate validation constraints at build time. Supported constraint tags from `@webergency-utils/typechecker` include:

Constraint Tag Applies To Description Example
MinLength<N> / MaxLength<N> string Restricts the string character length. string & MinLength<8>
Minimum<N> / Maximum<N> number Imposes numeric boundaries (inclusive). number & Minimum<18>
ExclusiveMinimum<N> / ExclusiveMaximum<N> number Numeric boundaries (exclusive). number & ExclusiveMinimum<0>
MultipleOf<N> number Asserts value is divisible by N. number & MultipleOf<5>
Format<'email' | 'uuid' | 'date'> string Enforces formatted validations. string & Format<'email'>
MinItems<N> / MaxItems<N> array Validates arrays bounds. string[] & MinItems<2>
UniqueItems array Requires unique items. number[] & UniqueItems

Let's view a comprehensive controller mapping parameters bindings and validation:

src/controllers/customer.controller.ts 
import { Controller, Post, Get, Body, Param, Query, Header } from '@webergency-utils/server';
import { MinLength, Format, UniqueItems } from '@webergency-utils/typechecker';

interface Address {
  city: string;
  zip: string;
}

interface RegisterDto {
  email: string & Format<'email'>;
  password: string & MinLength<8>;
  tags: string[] & UniqueItems;
  address?: Address;
}

@Controller('/customers')
export class CustomerController {

  @Post('/register')
  async register(@Body('strict') body: RegisterDto) {
    // Binds and validates request body. Strict mode rejects extra keys.
    return { registered: true, body };
  }

  @Get('/:id')
  details(
    @Param('id') id: string & Format<'uuid'>, 
    @Query('fields') fields?: string[],
    @Header('x-api-key') apiKey?: string
  ) {
    return { id, fields, apiKey };
  }
}

Validation Errors Format

If an incoming client request fails parameter, header, or query validation checks, Webergency immediately aborts processing. It returns an HTTP 400 Bad Request response with standard JSON detailing the failures:

Response payload (HTTP 400) 
{
  "success": false,
  "errors": [
    {
      "path": "body.email",
      "expected": "Format<email>",
      "value": "invalid-email-address"
    }
  ]
}

Each error object contains:

  • path: Identifies where the parameter check failed (e.g. body.email, query.limit, params.customerId).
  • expected: The type checker validation constraint that was violated (e.g., Format<email>, MinLength<8>, number).
  • value: The actual value received that failed to validate.

Dependency Injection & Provider Scopes

Webergency supports standard injection using `@Injectable()` and `@Inject()`. You can specify three lifetime scopes:

  • Scope.DEFAULT (Singleton): A single instance is instantiated at startup and shared application-wide.
  • Scope.TRANSIENT: A new instance is created every time it is injected.
  • Scope.REQUEST: A new instance is created for each incoming request, sharing it throughout the request execution context.
src/services/transient.service.ts 
import { Injectable, Scope } from '@webergency-utils/server';

@Injectable({ scope: Scope.TRANSIENT })
export class TransientService {
  public id = Math.random().toString(36).substr(2, 9);
}
src/modules/app.module.ts 
import { Module, Global } from '@webergency-utils/server';
import { TransientService } from '../services/transient.service.js';
import { CustomerController } from '../controllers/customer.controller.js';

@Global() // Makes the module's exported providers globally importable
@Module({
  controllers: [CustomerController],
  providers: [TransientService],
  exports: [TransientService]
})
export class AppModule {}

Custom Providers

Webergency supports standard custom providers definitions inside the providers array of modules. This allows you to override classes, supply configuration constants, or generate dynamic values dynamically:

Inject static constant values, configuration setups, or third-party instances using useValue: 

@Module({
  providers: [
    {
      provide: 'APP_CONFIG',
      useValue: { env: 'production', apiVersion: 'v1.2' }
    }
  ]
})
export class ConfigModule {}

Swap the default provider class with an alternative implementation (e.g. testing mock logger) using useClass: 

@Module({
  providers: [
    {
      provide: LoggerService,
      useClass: VerboseLoggerService
    }
  ]
})
export class LoggerModule {}

Generate dynamic configurations, async initializations, or conditional structures using useFactory: 

@Module({
  providers: [
    {
      provide: 'DATABASE_CONNECTION',
      useFactory: (logger: LoggerService) => {
        return new DatabaseConnection({ debug: true }, logger);
      },
      inject: [LoggerService]
    }
  ]
})
export class DatabaseModule {}

Request-Scoped Injections

By specifying Scope.REQUEST inside provider options, Webergency will create a new instance of the provider for each incoming HTTP or RPC request context. These instances are stored in the active request memory context and garbage collected automatically when the request finishes.

Bubble-Up Scope Enforcements

If a singleton provider injects a request-scoped provider, the container automatically bubbles up the scope of the parent provider to request-scoped as well. This prevents request-scoped data leaks across different active connections.

Lifecycle Hooks

Webergency provides structural lifecycle hooks to handle application bootstrap and graceful shutdowns. Injectable providers and modules can implement hook interfaces:

Lifecycle Interface Method Signature Execution Stage
OnModuleInit onModuleInit(): void | Promise<void> Called after modules are initialized, before the adapter starts listening. Perfect for database pool configurations.
OnApplicationBootstrap onApplicationBootstrap(): void | Promise<void> Called after the server adapter successfully listens on the port.
OnModuleDestroy onModuleDestroy(): void | Promise<void> Called when graceful shutdown is initiated.
BeforeApplicationShutdown beforeApplicationShutdown(signal?: string): void | Promise<void> Called during the shutdown flow. Receives system OS signal.
OnApplicationShutdown onApplicationShutdown(signal?: string): void | Promise<void> Called at the end of graceful shutdown. Used to safely close database connections and file channels.

Here is a complete database service implementation implementing bootstrap and shutdown hooks:

src/services/db.service.ts 
import { Injectable, OnModuleInit, OnApplicationShutdown } from '@webergency-utils/server';

@Injectable()
export class DatabaseService implements OnModuleInit, OnApplicationShutdown {
  private connectionPool: any;

  async onModuleInit() {
    console.log('🔌 Establishing database connection pool...');
    this.connectionPool = await mockConnect('mongodb://127.0.0.1:27017/app');
    console.log('✅ Database connected.');
  }

  async onApplicationShutdown(signal?: string) {
    console.log(`💤 Graceful shutdown initiated (Signal: ${signal}). Closing DB pool...`);
    await this.connectionPool.close();
    console.log('🛑 Database pool closed safely.');
  }
}

Guards & Interceptors

Protect and intercept flows at class or endpoint levels. 

import { Guard, Injectable, Header } from '@webergency-utils/server';

@Injectable()
export class RoleGuard implements Guard {
  
  // Guards support parameter decorators to parse headers, queries, body, etc.
  use(@Header('x-user-role') role: string) {
    if (role !== 'admin') {
      throw { code: 403, message: 'Requires admin permissions' };
    }
  }
}
import { Interceptor, Injectable } from '@webergency-utils/server';

@Injectable()
export class MetricsInterceptor implements Interceptor {
  
  async intercept(request: any, next: () => Promise<any>) {
    const start = performance.now();
    try {
      const result = await next(); // Execute handler or next interceptor
      const duration = performance.now() - start;
      console.log(`Request succeeded in ${duration.toFixed(2)}ms`);
      return result;
    } catch (err) {
      console.error('Request failed:', err);
      throw err;
    }
  }
}

Exception Filters & Custom Error Mapping

Webergency's zero-reflection compilation design keeps runtime overhead to a minimum. Instead of custom @Catch() decorators, exception filtering and custom error mappings are implemented using standard Interceptors.

Interceptors wrap the execution pipeline (including guards, parameter validation, and endpoint handlers). This gives you the ability to catch runtime exceptions, inspect returned responses (such as validation failures), and map them to unified API errors.

Default Exception Behavior

By default, any unhandled error thrown inside controllers, guards, or interceptors is caught by the request processor:

  • If the thrown object has a status or code property, it is used as the HTTP status (defaults to 500).
  • The response payload is automatically formatted as JSON: err.data (if present) or { success: false, error: err.message }.
  • For parameter and payload validation errors, the compiler-generated code directly returns an HTTP 400 Bad Request response with details without throwing a runtime error.
src/interceptors/exception.filter.ts 
import { Interceptor, Injectable } from '@webergency-utils/server';

@Injectable()
export class HttpExceptionFilter implements Interceptor {
  async intercept(request: any, next: () => Promise<any>) {
    try {
      return await next();
    } catch (err: any) {
      const status = err.status || err.code || 500;
      const message = err.message || 'Internal server error';
      
      console.error(`[Error] ${request.method} ${request.url}:`, err);

      // Return a formatted, sanitized error response
      return new Response(
        JSON.stringify({
          success: false,
          statusCode: status,
          message: status === 500 ? 'Internal server error' : message,
          timestamp: new Date().toISOString()
        }),
        {
          status,
          headers: { 'Content-Type': 'application/json' }
        }
      );
    }
  }
}
src/interceptors/validation-sanitizer.filter.ts 
import { Interceptor, Injectable } from '@webergency-utils/server';

@Injectable()
export class ValidationSanitizerFilter implements Interceptor {
  async intercept(request: any, next: () => Promise<any>) {
    const response = await next();

    // Intercept compiler-generated validation errors (HTTP 400)
    if (response.status === 400) {
      const clone = response.clone();
      try {
        const data = await clone.json();
        if (data.success === false && data.errors) {
          // Simplify compiler-generated validation formats for clients
          return new Response(
            JSON.stringify({
              success: false,
              message: 'Validation failed',
              details: data.errors
            }),
            {
              status: 400,
              headers: { 'Content-Type': 'application/json' }
            }
          );
        }
      } catch (e) {
        // Response was not JSON, return as-is
      }
    }

    return response;
  }
}

Registering Filter Interceptors

Bind exception filtering interceptors locally to endpoints or controllers using the @Intercept decorator, or register them globally.

src/controllers/user.controller.ts 
import { Controller, Get, Intercept } from '@webergency-utils/server';
import { HttpExceptionFilter } from '../interceptors/exception.filter.js';

@Controller('/users')
@Intercept(HttpExceptionFilter)
export class UserController {
  @Get('/:id')
  async getUser() {
    throw { status: 404, message: 'User not found' };
  }
}

CORS & Security Configuration

Configure endpoint security boundaries natively. Decorator `@Security()` enables headers mapping, rate limiting, and request timeouts in a single declaration:

src/controllers/api.controller.ts 
import { Controller, Get, Security, Cors } from '@webergency-utils/server';

@Controller('/secure-api')
@Cors({
  origin: ['https://app.webergency.org'],
  allowedHeaders: ['Content-Type', 'Authorization'],
  credentials: true
})
@Security({
  maxBodySize: '1mb',          // Maximum body limit
  timeout: 800,                // Abort request after 800ms
  allowedContentTypes: ['application/json'],
  rateLimit: {
    max: 100,
    window: 60000              // 100 requests per minute
  },
  frameguard: 'deny',          // X-Frame-Options: DENY
  noSniff: true,               // X-Content-Type-Options: nosniff
  referrerPolicy: 'no-referrer'
})
export class ApiController {

  @Get('/data')
  loadData() {
    return { confidential: 'highly' };
  }
}

Mutual TLS (mTLS) & Client Certificate Verification

Webergency supports standard mutual TLS (mTLS) client certificate verification natively in Bun and Node.js. Enable validation by providing requestCert and rejectUnauthorized toggles inside your Server boot options:

src/main.ts (mTLS Server Boot) 
import { Server } from '@webergency-utils/server';
import * as fs from 'node:fs';

const server = new Server({
  port: 443,
  tls: {
    key: fs.readFileSync('server-key.pem'),
    cert: fs.readFileSync('server-cert.pem'),
    ca: fs.readFileSync('ca-cert.pem'), // Trusted CA to authorize client certificates
    requestCert: true,                 // Request client cert
    rejectUnauthorized: true           // Block requests without a valid client cert
  }
});

await server.start();

WebSockets & Heartbeats

Assign real-time events over bidirectional WebSockets using `@Ws()`. The decorator schedules heartbeats to automatically disconnect inactive connections:

src/controllers/chat.controller.ts 
import { Controller, Ws, ServerWebSocket, Param } from '@webergency-utils/server';

@Controller('/chat')
export class ChatController {

  @Ws('/connect/:channel', {
    pingInterval: 20000,  // Send ping frame every 20s
    pingTimeout: 5000,    // Await pong response for 5s (disconnects on timeout with code 1002)
    maxPayload: 2048      // Closes connection with code 1009 if a message exceeds 2KB
  })
  onConnect(ws: ServerWebSocket, @Param('channel') channel: string) {
    ws.send(`Welcome to channel #${channel}`);

    ws.on('message', (msg) => {
      ws.send(`Broadcast: ${msg}`);
    });

    ws.on('close', (code, reason) => {
      console.log(`WebSocket connection closed: ${code} - ${reason}`);
    });
  }
}

Server-Sent Events (SSE)

Create server push events using HTTP GET channels using `@Sse()`. 

import { Controller, Sse } from '@webergency-utils/server';

@Controller('/metrics')
export class MetricsController {

  @Sse('/live')
  async *stream() {
    while (true) {
      await new Promise(resolve => setTimeout(resolve, 1000));
      yield {
        event: 'stats',
        data: { cpu: Math.random() * 100, memory: process.memoryUsage().heapUsed }
      };
    }
  }
}
const eventSource = new EventSource('http://localhost:3000/metrics/live');

eventSource.addEventListener('stats', (event) => {
  const stats = JSON.parse(event.data);
  console.log('Metrics update:', stats);
});

eventSource.onerror = (err) => {
  console.error('SSE Stream error:', err);
  eventSource.close();
};

Microservices (RPC) & TCP Messaging

Configure decoupled networks using built-in RPC listeners over TCP sockets. Intercept event envelopes and perform compiled schema payloads validation on incoming requests automatically:

src/controllers/rpc-math.controller.ts 
import { Controller, MessagePattern, Payload } from '@webergency-utils/server';

interface MultiplyDto {
  x: number;
  y: number;
}

@Controller()
export class RpcMathController {

  @MessagePattern('math.multiply')
  multiply(@Payload() payload: MultiplyDto) {
    return payload.x * payload.y;
  }
}

Swagger / OpenAPI 3.0.0 Spec Generation

A zero-dependency OpenAPI 3.0.0 documentation exporter runs automatically alongside compilation. The Swagger generator:

  • Parses actual TypeScript typings of request body objects and query objects, and compiles them to JSON schemas.
  • Derives formats (like Format<'email'>, Format<'uuid'>) and constraints directly into fields (e.g. minLength, exclusiveMinimum).
  • Exports the final compilation to a standard swagger.json in the output directory.
